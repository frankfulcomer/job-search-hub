## 1. What Got Built: Feature Timeline

Phase 1's scope is the eleven functional requirements (FR-001–FR-011) and
seven non-functional requirements (NFR-001–NFR-007) defined in
`docs/mvp-requirements.md`. Every FR was implemented, independently reviewed,
and committed. The delivery order did not follow requirement numbering —
each slice was chosen deliberately based on what the next slice needed to
exist first (e.g., FR-009's archive state had to exist before FR-002's
duplicate-detection scan could meaningfully decide whether to include
archived applications).

| Order | Requirement | Commit | Notable design choice |
|---|---|---|---|
| 1 | Project skeleton, SQLite persistence foundation | `9034792`, `59348ca` | Six-entity 3NF schema, STRICT tables, millisecond-UTC timestamps, normalized-uniqueness expression indexes — recorded in **ADR-0001** |
| 2 | FR-001 (Record an Application) | `d9a6d8a`, `5f73add`, `db37fde` | Resolve-or-create pattern for company/source/location, sharing the same normalized-matching SQL as the database's own uniqueness index |
| 3 | FR-003 (View Applications) | `5638f5f` | Single windowed query using `ROW_NUMBER() OVER (PARTITION BY application_id ORDER BY effective_at DESC)` for current-status derivation, verified via `EXPLAIN QUERY PLAN` to avoid N+1 |
| 4 | FR-005 (View Application Details) | `c8143ba` | Job location and company headquarters fetched via two independent `LOCATION` joins so they remain visibly distinct even when identical |
| 5 | FR-006 (Edit an Application) | `80e6d1a` | Two-step HTTP confirmation flow for shared-company headquarters changes; editing the Company field reassociates rather than renames |
| 6 | FR-007 (Update Application Status) | `20558fd` | Required **zero new current-status derivation code** — the FR-003 windowed query already handled backdated entries correctly |
| 7 | FR-008 (Correct Application Status History) | `ac15447` | Deliberately sequenced right after FR-007, since FR-007 made frequent user-driven history entry possible for the first time with no correction mechanism |
| 8 | FR-009 (Archive and Restore) | `7a9529a` | True no-ops when already in the target state, so re-archiving doesn't advance `last_updated_at`; asymmetric confirmation (archive confirms, restore doesn't) per requirement text |
| 9 | FR-002 (Detect Potential Duplicates) | `f053563` | Deferred until FR-009 existed, since "does archiving affect duplicate matching" was newly answerable; matching scans both active and archived applications |
| 10 | FR-004 (Search and Filter Applications) | `77f8dc2` | Six design decisions resolved in a dedicated planning session *before* implementation began, at explicit user request, after the agent recommended against attempting the full slice in the remaining session capacity |
| 11 | FR-011 (Validate Input and Handle Errors) | `06b3c76`, later completed by `d98e6a2` | Job-URL validation via stdlib `urllib.parse` (no new dependency); compensation-basis and compensation-range messaging added as an *earlier* application-level layer alongside the existing database `CHECK` constraints, not a replacement for them |
| 12 | FR-010 (Manage and Reuse Reference Data) | `fc4a200` | Native HTML5 `<datalist>` chosen over a `<select>` dropdown or a separate admin screen — the only option that allows both selecting an existing value and typing a new one with zero JavaScript |

By the end of the documented work, all eleven FRs are fully satisfied. FR-010
and FR-011 were the two that required a dedicated **Phase 1 MVP completion
audit** to surface as incomplete — both had substantial groundwork already in
place (normalized data-layer reuse for FR-010; most of FR-011's validation
rules) but were missing specific, testable pieces of the requirement text.

NFR-001, 002, 003, 005, 006, and 007 were assessed as fully satisfied. **NFR-004
(Browser Support)** remains partially unverified: Chromium compatibility was
manually checked once, early, against the initial application skeleton, and
was never re-verified against the full current feature set — full
browser-level verification is explicitly out of this repository's scope,
belonging to a separate `job-search-hub-tests` Selenium repository that was
never created during this effort.

## 2. QA/Review Findings and Defects Corrected

Every implementation slice ended with an independent review before commit.
This was not a formality — the reviews found real defects, several of them
significant, in nearly every slice. Listed here by category rather than by
slice, since the pattern across slices is itself informative.

### Data integrity and correctness

- **FR-006 (High severity):** reassigning an application's company did not
  refresh the headquarters fields to the newly-selected company, directly
  contradicting architecture.md's requirement that a company change display
  the new company's own headquarters. Two reachable paths existed: proposing
  to silently overwrite a *shared* company's real headquarters via the
  confirmation flow, and applying a stale headquarters value to a *new or
  unshared* company with no confirmation gate at all. Fixed by decoupling
  company reassignment from headquarters editing entirely.
- **FR-001 (Medium, found during FR-007 work):** the default `now` used
  whenever a request didn't inject one was constructed as
  `datetime.now(timezone.utc)`, then compared against a locally-meaning
  `application_date`. For several hours daily in any negative-UTC-offset
  timezone, an ordinary same-day submission incorrectly required an explicit
  effective time. Fixed by changing the default to
  `datetime.now().astimezone()`. The first two regression tests written for
  this fix were themselves found, on review, not to be reliably
  deterministic — one only failed inside the narrow vulnerable window, the
  other never exercised the buggy code path at all — and were replaced with
  a test that asserts on `datetime.now`'s call signature directly via
  `unittest.mock.patch`, independent of wall-clock timing.

### Security

- **FR-005 (self-caught during implementation, not by a separate reviewer):**
  `job_url` had no entry-time format validation and was rendered directly
  into an `href`, so a stored `javascript:...` value became an executable
  link — a stored XSS path. Fixed with a `job_url_is_safe_link` property
  allow-listing only `http`/`https` schemes; this defense-in-depth check was
  preserved even after FR-011 later added entry-time URL validation, since it
  still protects data that predates that validation or reaches the database
  by another path.

### Boundary and error handling

- **Recurring `OverflowError` pattern:** an oversized integer ID exceeding
  SQLite's 64-bit `INTEGER` range raised an unhandled `OverflowError` (an
  unhandled 500) instead of being treated as "no such row." This was found
  and fixed **twice**, independently, at two different entry points — first
  for `application_id` in the FR-005 detail view, then again for the
  `job_location` filter parameter during FR-004 — confirming it as a
  systemic pattern (any code path converting user input into a SQLite
  integer lookup is a candidate) rather than a one-off bug. Documented as
  such in `docs/lessons-learned.md`.
- **FR-004:** a date-range validation error marked only the `date_from`
  field as `aria-invalid`, not `date_to`, even though the violation is a
  relationship between both fields. Fixed by attributing the error to a
  synthetic `date_range` field that marks both inputs.

### Test quality and coverage gaps

- **FR-008:** independent review found two coverage gaps that were not
  production defects but real regression-protection gaps: no test verified
  a status-history record's own `created_at` was preserved on correction,
  and `delete_status_history` had no cross-application isolation test at
  either layer (notable since delete is destructive).
- **FR-002:** one existing test assertion was found to be tautologically
  true — structurally incapable of failing — and was explicitly left
  unchanged, since fixing an unrequested test-quality issue wasn't part of
  the authorized task. This restraint (documenting a finding without acting
  on it unilaterally) recurs throughout the later, more formalized review
  process.
- **The `archived_at` timing flake** (see the CI section below) illustrates
  the same discipline at a larger scale: a CI failure on a commit that only
  touched documentation was investigated to a precise, evidence-based root
  cause (SQLite/Python's millisecond timestamp truncation, not a rounding
  error) before any test code was changed.

### Verification discipline

Starting with the FR-006 review and continuing through every subsequent
slice, defects and their regression tests were verified as *genuinely*
protective — not merely passing — by deliberately reintroducing the defect
(via `unittest.mock.patch`, editing a disposable scratch copy, or reverting
the fix) and confirming the test failed for the expected reason before
restoring the fix. This technique caught, among other things, two
non-deterministic timing tests (described above) that would otherwise have
looked like adequate coverage. It is now a documented rule in
`docs/development-process.md`'s Testing and Verification section.

## 3. Continuous Integration: From Absent to Green, With a Real Incident

CI is a small but illustrative story on its own:

1. **Gap identified.** The first Phase 1 MVP completion audit found no CI
   workflow existed anywhere in the repository's history, despite
   `docs/test-strategy.md`'s explicit requirement for one — flagged as the
   single most significant test-strategy gap, since the repository already
   had a real GitHub remote and nothing else was blocking it.
2. **Workflow added (`ff82b73`).** A minimal `.github/workflows/ci.yml` —
   install dependencies, run the full `pytest` suite, fail on any failure,
   trigger on push and pull request. Deliberately excluded coverage
   tooling, linting, matrix builds, and Selenium, none of which were
   required by `test-strategy.md`.
3. **Critical bug found by independent review, before the first push.**
   `.gitignore`'s blanket `*.sql` rule (intended to exclude database
   dumps) also matched `src/job_hub/schema.sql` — the application's own
   schema file, read at startup by every request. It had **never been
   committed**, for the entire project history up to that point, and the
   gap was invisible locally because the file existed on every developer's
   disk regardless of Git tracking. A true fresh `git clone` (reproducing
   what `actions/checkout` does) confirmed the bug directly: 432 test
   errors, all `FileNotFoundError`. Fixed with a targeted negation rule in
   `.gitignore` (`!src/job_hub/schema.sql`) rather than a full rewrite of
   the ignore pattern, and the schema file was committed for the first
   time alongside the workflow (`ff82b73`).
   - A secondary finding from the same review: the *first* attempt to
     validate the workflow locally used a fresh virtual environment, which
     only isolates Python package state, not Git-tracked-file state — it
     could not have caught the `.gitignore` bug. This distinction ("a
     fresh venv is not equivalent to a fresh checkout") is now documented
     in `lessons-learned.md`.
4. **A genuine CI failure, correctly triaged.** After several clean runs,
   pushing a documentation-only commit (`3d4290d`) triggered a CI failure
   on `tests/test_application_archive_routes.py`. Rather than assuming the
   documentation change caused it (it touched no application code), the
   failure was investigated to a specific root cause: SQLite and Python
   both **truncate** (not round) sub-millisecond precision when formatting
   timestamps for storage, so a persisted `archived_at` value could
   legitimately land up to ~1ms *before* a `before`-style wall-clock bound
   captured with full microsecond precision — a representation-precision
   artifact, not a timing bug. Fixed by widening the test's tolerance to
   match the documented millisecond storage precision (`ADR-0001`), not by
   loosening the assertion arbitrarily — verified via 3,000-trial direct
   measurement against the actual formatting function, and via mutation
   testing confirming the widened tolerance still catches a genuinely
   stale (10-second-off) timestamp.
5. **Result:** five CI runs total by the end of the documented work — one
   failure (the flake above, since fixed and reverified green), four
   successes.

## 4. Documentation and Process Evolution

Documentation accuracy was treated as a first-class deliverable, not an
afterthought, and several real staleness problems were found and fixed:

- **`README.md`** was found to contain its entire content duplicated
  verbatim, back-to-back with no line break between the copies, describing
  a FastAPI/PostgreSQL/SQLAlchemy stack that was never adopted and a
  `Status: Planning` that predated most of the implemented work. Fixed in
  two passes: an initial correction, then a further refinement after an
  independent review found the corrected version still overstated test
  coverage for one NFR (browser verification) — narrowed to name that gap
  explicitly rather than claim blanket coverage.
- **`docs/roadmap.md`** was found, during a later full-repository
  documentation audit, to still list "Status history" and "Compensation
  and employment-type information" as *future* Phase 2 work, even though
  both were fully implemented Phase 1 scope per `mvp-requirements.md`'s own
  Scope section — a case of documentation drifting behind an
  already-shipped feature rather than ahead of it.
- **`docs/lessons-learned.md`**, empty since project start, was populated
  with twelve lessons drawn directly from real incidents in the journal —
  not general best-practice advice — including the recurring
  `OverflowError` pattern, the timezone-frame mismatch, the `.gitignore`
  schema bug, and the documentation-staleness pattern itself (noting that
  it had occurred at three separate, unrelated levels: a code comment, the
  README, and the roadmap).
- **`docs/development-process.md`** grew substantially over the course of
  the effort, described in the next section.

Each of these fixes went through the same independent-review discipline as
code changes — including, in one case, a reviewer catching that the
implementer's own "remaining gap" report was itself stale (a rule that had
already been added to `Testing and Verification` was mistakenly reported as
still missing, carried forward from an earlier finding without re-checking
the current file). That correction is itself now part of the documented
record, in keeping with the project's stated principle of preserving
superseded decisions rather than silently rewriting history.

## 5. Significant Design Decisions

A sample of the decisions that shaped the implementation, beyond the
per-feature choices already listed in Section 1:

- **Reference-data reuse scope (FR-010):** suggestion lists for
  company/source/location selection deliberately include records no longer
  linked to any current application, distinct from FR-004's filter-option
  lists, which deliberately exclude them. Two functions with similar names
  and genuinely different semantics were kept separate rather than
  unified behind a parameter, to avoid conflating the two meanings of
  "existing."
- **Validation layering (FR-011):** every new application-level check
  (URL format, compensation basis, compensation range) was added
  *alongside* its corresponding database constraint, never replacing it —
  consistent with `architecture.md`'s explicit "database constraint plus
  application validation" requirement for these rules.
- **Schema initialization made automatic, and the reasoning recorded as a
  revision rather than a silent change:** the database schema was
  originally initialized only on explicit request (`flask init-db`), to
  keep application-factory tests from implicitly touching a database file
  on disk. Once the Create Application route existed, that trade-off meant
  a fresh checkout would fail on first real use. `ADR-0001` documents the
  change to unconditional, idempotent initialization inside `create_app()`
  as an explicit revision of the earlier decision — including why the
  original choice had been made and why it no longer held — rather than
  quietly replacing it.
- **Scope discipline over completeness:** on at least two occasions (FR-002's
  review, and FR-011's initial implementation), a real, related issue was
  identified and explicitly left unfixed because it fell outside the
  authorized task — not silently ignored, but reported and deferred with a
  documented reason.

## 6. Evolution of the Human/AI Collaboration and Change-Control Model

The working process visibly matured over the course of the effort, moving
from an already-disciplined baseline to a fully codified one:

**Early slices** (FR-001 through roughly FR-009) already established the
core pattern that held for the rest of the project: implement a scoped
slice, run tests, get an independent review, fix or explicitly defer
findings, update the journal, and stop — commits happened only on explicit
instruction, and several early user corrections (a current-status sort key
implemented as lifecycle order instead of the intended alphabetical order;
an FR citation that didn't match the described work) were caught and fixed
rather than argued past.

**The first completion audit** (after FR-002) introduced a new practice:
periodically stepping back from feature-by-feature work to re-verify the
*whole* repository against requirements and architecture from scratch. This
practice repeatedly found things incremental work had missed — not just
once, but on nearly every occurrence it was used, including gaps in its own
prior output (the rollback-coverage claim in the first audit was corrected
by the second; the "remaining gap" mis-report described in Section 4 was
corrected within the same task that produced it).

**The later stage of the effort** made the previously-implicit review
discipline explicit and durable, by writing it into
`docs/development-process.md` itself:

- An **`AI-Assisted Change Control`** section was added, stating explicitly
  that routine, reversible, read-only operations (searching files, `git
  status`/diff/log, running tests) don't require repeated confirmation once
  a task is authorized — deliberately distinguished from an enumerated list
  of control boundaries that always do: expanding scope, committing,
  pushing, initiating CI, destructive Git operations, deleting or replacing
  project records, and taking on unrelated corrective work found along the
  way. Completing one authorized stage was made explicit as *not* implying
  authorization for the next.
- Independent review was formalized as requiring a **fresh** read of
  governing documentation and the actual diff — not the implementer's own
  summary or a prior compacted narrative — with findings classified by
  severity and required to remain traceable across review iterations rather
  than silently disappearing.
- Failure handling was formalized to require investigation before
  correction, and to explicitly separate "authorized to investigate" from
  "authorized to fix."
- A **`Transcript Preservation and Provenance`** section was added — the
  first time the project's own development transcripts were treated as a
  documented category of project record, with rules for verbatim
  preservation, consolidation of overlapping exports, and provenance
  tracking. This document is itself the first artifact produced under that
  section's `Highlights` rules.

This progression — informal-but-consistent discipline, then periodic
whole-repository audits, then codified written rules — is itself one of the
more notable outcomes of the Phase 1 effort, independent of the application
code produced.
