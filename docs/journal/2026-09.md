# Project Journal — September 2026

## 2026-09-19 — Project Initiation

### Origin

Job Search Hub originated from several related needs that converged into a single project.

The existing spreadsheet-based Job Search Hub had grown increasingly complex as additional applications, companies, recruiter contacts, activities, and supporting information were added. A relational database was identified as a more appropriate long-term system of record and as an opportunity to apply and demonstrate SQL skills.

A separate need existed for a realistic application against which Selenium automation could be developed. Rather than creating a disposable demonstration application, the decision was made to build an application that serves an actual job-search need.

Job Hunter also requires a persistent system with which future job-discovery capabilities can integrate. Job Search Hub can provide that backend and become the authoritative destination for opportunities discovered through Job Hunter or other sources.

### Expanded Direction

Discussion of the initial concept identified several longer-term opportunities.

Repeatable job-search decisions currently requiring manual or AI-assisted evaluation may eventually be moved into deterministic application logic. Potential examples include compensation thresholds, commute evaluation, duplicate detection, follow-up timing, opportunity scoring, and application workflow.

AI may remain useful for tasks involving interpretation of unstructured or ambiguous information, such as extracting structured requirements from job descriptions. The long-term objective is to use deterministic, testable logic where practical and reserve AI for tasks where it provides meaningful value.

Reporting and business intelligence were also identified as natural extensions of the relational data model. PostgreSQL can support operational SQL reporting, while Power BI is being considered for future analytical dashboards. Historical application, evaluation, activity, and outcome data may eventually be used to evaluate both job-search performance and the effectiveness of the application's decision logic.

### Initial Technology Direction

The current technology direction includes:

- Python
- FastAPI
- PostgreSQL
- SQLAlchemy
- REST APIs
- Pytest
- Selenium
- Power BI for future business intelligence work

Python was favored because it can support the application backend, automated testing, future data analysis, and potential machine-learning work while remaining relatively readable during review of AI-assisted implementation.

Technology selections will be formalized through Architecture Decision Records as architecture planning progresses.

### Development Approach

An incremental development strategy was selected.

The first objective will be a minimum viable product rather than implementation of the complete long-term vision. Subsequent capabilities will be introduced through planned releases while preserving a usable application.

The Linux development machine will serve as the primary build environment. The application will periodically be exercised on the Windows environment as development progresses.

The project will use an AI-assisted engineering workflow. ChatGPT will primarily support requirements, architecture, test strategy, documentation, implementation planning, and review. Claude will primarily support implementation. Product direction, architectural approval, exploratory testing, acceptance, and release decisions remain subject to human review.

AI involvement will be documented explicitly so that project documentation does not imply either greater or lesser human contribution than actually occurred.

### Documentation Approach

Project documentation will be maintained within the repository from the beginning of the project.

Documentation will use Markdown and a professional, impersonal technical writing style. Personal names and first-person language will be avoided.

The repository will include:

- Product and architecture documentation
- Architecture Decision Records
- A chronological project journal
- Lessons learned
- Development-process documentation
- Release documentation

Decisions that are later replaced should generally remain in the historical record with their superseded status rather than being removed.

### Source Control and Publication

The project was initialized locally as a Git repository before implementation began.

The GitHub repository will initially remain private. This provides an opportunity to develop and review the application without prematurely exposing unfinished work or private information.

A public release is planned after the MVP reaches an appropriate level of quality and the complete repository and Git history have undergone a privacy and security review.

The project will remain a single evolving repository rather than creating separate repositories for each application version. Stable releases will be identified through version tags.

### Privacy

Privacy is a design requirement.

Real job-search information must remain separate from publicly shareable source code and documentation. Synthetic data will eventually support development, automated testing, screenshots, demonstrations, and portfolio presentation.

Before any public release, the repository will be reviewed for personal information, credentials, private communications, real job-search data, database exports, logs, screenshots, metadata, and other information that should not be publicly exposed.

### Current Status

The local Git repository and initial documentation structure have been created.

Initial versions of the following documents have been prepared:

The next major activity is MVP planning, including scope, domain modeling, architecture, privacy requirements, and test strategy.

### Application List

- Implemented the Phase 1 application list view (FR-003), including default and
  column-based sorting and pagination at the documented page size, since
  FR-003 specifies both as part of "View Applications" rather than as
  ambiguous behavior.
- Confirmed scope: FR-004 (search and filter, including active/archived/all
  record-state filtering) remains a separate, deferred slice. Archived
  applications are excluded from this list (`archived_at IS NULL`) pending
  FR-004's record-state filtering and the not-yet-implemented archive/restore
  workflow that sets `archived_at`.
- Resolved two sort-key ambiguities left open by FR-003, which does not define
  sort keys for compound or reference-backed columns:
  - "Job location" sorts by its displayed components, city, then
    state/province, then country.
  - "Current status" sorts alphabetically by the displayed status name
    (`STATUS.name`), not by `STATUS.display_order`'s lifecycle sequence.
    Added a regression test (`test_list_applications_status_sort_is_alphabetical_not_lifecycle_order`)
    using a status pair (CLOSED/OFFER) whose alphabetical and
    lifecycle orderings disagree, so the distinction is actually exercised.
- Job location displays as its non-blank components joined with ", "; an
  em dash (—) represents a missing optional value (job location, work
  arrangement) in the list. Neither format is specified by the requirements.
- Current status is derived from the latest `application_status_history`
  record per application in a single query
  (`ROW_NUMBER() OVER (PARTITION BY application_id ORDER BY effective_at DESC)`),
  matching architecture.md's derivation rule and avoiding N+1 queries against
  reference data.
- Changed the create-application success redirect from the home page to the
  new list page, since a meaningful destination now exists.
- Added service-level tests (`list_applications`) and route/template tests
  covering empty state, displayed field values, reference-data display,
  default and column ordering (including the two resolved sort-key
  ambiguities), pagination boundaries, archived-application exclusion, and

### Application Detail View

- Implemented the Phase 1 application detail view (FR-005: "View Application
  Details"). The implementation request cited "FR-002" but described the
  detail view by name; FR-002 is actually "Detect Potential Duplicate
  Applications," a separate, still-deferred requirement. Implemented what was
  unambiguously described (FR-005) and corrected the citation here rather
  than silently going along with it or implementing FR-002 instead.
- Added `GET /applications/<application_id>`, presenting the four documented
  sections (Application; Company and Location; Original Posting; History and
  Notes) using `<dl>` label/value pairs and a status-history `<table>`.
- Current status is derived from the already-fetched, ascending-ordered
  status history (the last entry, guaranteed unique by
  `UNIQUE(application_id, effective_at)`) rather than a second derivation
  query, keeping the "same derivation" rule from architecture.md satisfied
  without adding a redundant query.
- Company headquarters location and job location are fetched via two
  independent joins to `LOCATION` (by `company.hq_location_id` and
  `application.job_location_id`), so they display as distinct fields even
  when they resolve to the same normalized location row, per architecture.md.
  Verified with a test where both are set to the same city/state/country.
- The status-history row matching the current status is marked both visually
  (a "(current)" label) and with `aria-current="true"`, so "the application's
  current status shall be clearly identifiable" holds for assistive
  technology, not only sighted users.
- Compensation fields (minimum, maximum, basis) are shown individually only
  when present, following FR-005's "when available" wording literally rather
  than inventing a combined range-display format.
- The detail query does not filter by `archived_at`: FR-009 describes
  archiving as affecting default *list* visibility while explicitly
  preserving full application information, so a detail page reachable by ID
  should not depend on archive state. Currently moot (no route sets
  `archived_at` yet), but recorded so it isn't revisited as an unexplained
  assumption once archive/restore lands.
- Closed a gap flagged during the Application List slice: FR-003 requires
  that "selecting an application shall provide access to the complete
  application detail view," which couldn't be implemented until the detail
  view existed. The list's job-title cell is now a link to the detail page.
- Self-review caught a real stored-XSS-via-`href` issue: `job_url` has no
  format validation (deferred since the Create Application slice), and
  rendering it directly into `href` allowed a stored `javascript:` URL to
  become an executable link. Fixed by only rendering `job_url` as a clickable
  `<a>` for `http`/`https` schemes; any other value displays as inert
  (escaped) text. Added both service-level and route-level regression tests.
- Returns 404 for a nonexistent or non-integer application ID; not specified
  by FR-005 but necessary basic behavior for an ID-addressed resource.
- Added service-level tests (`get_application_detail`) and route/template
  tests covering core field display, missing-optional-field placeholders,
  the distinct-location case, status-history ordering and current-status
  marking, partial compensation presence, the job-URL scheme fix, list-to-
  detail navigation, and output escaping.
- Pytest result: 119 tests passed.
- Editing, status changes, archive/restore, FR-004 search and filter,
  reference-data management, and Selenium automation remain intentionally
  deferred.
- Independent review of the detail view found two medium-severity issues,
  both fixed before commit:
  - An oversized `application_id` in the URL (exceeding SQLite's 64-bit
    `INTEGER` range) raised an unhandled `OverflowError`, producing a 500
    instead of a 404. The route now catches `OverflowError` from
    `get_application_detail` and treats it as not found, since an
    out-of-range id can never match a row either way.
  - Compensation values stored as whole numbers displayed with a spurious
    trailing `.0` (e.g., "100000.0"), a side effect of `STRICT REAL` storage
    round-tripping through Python `float`. Added `compensation_min_display`/
    `compensation_max_display` formatting properties that drop the trailing
    `.0` for whole values while preserving genuine decimals (e.g., "45.5").
  - Added regression tests for both at the service and route level.
  - Pytest result after fixes: 124 tests passed.
