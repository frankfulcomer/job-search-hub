# Project Journal — September 2026

## 2026-09-19 — Project Initiation

### Origin

Job Search Hub originated from several related needs that converged into a single project.

The existing spreadsheet-based Job Search Hub had grown increasingly complex as additional applications, companies, recruiter contacts, activities, and supporting information were added. A relational database was identified as a more appropriate long-term system of record and as an opportunity to apply and demonstrate SQL skills.

A separate need existed for a realistic application against which Selenium automation could be developed. Rather than creating a disposable demonstration application, the decision was made to build an application that serves an actual job-search need.

Job Hunter also requires a persistent system with which future job-discovery capabilities can integrate. Job Search Hub can provide that backend and become the authoritative destination for opportunities discovered through Job Hunter or other sources.

### Expanded Direction

Discussion of the initial concept identified several longer-term opportunities.

Repeatable job-search decisions currently requiring manual or AI-assisted evaluation may eventually be moved into deterministic application logic. Potential examples include compensation thresholds, commute evaluation, duplicate detection, follow-up timing, opportunity scoring, and application workflow.

AI may remain useful for tasks involving interpretation of unstructured or ambiguous information, such as extracting structured requirements from job descriptions. The long-term objective is to use deterministic, testable logic where practical and reserve AI for tasks where it provides meaningful value.

Reporting and business intelligence were also identified as natural extensions of the relational data model. PostgreSQL can support operational SQL reporting, while Power BI is being considered for future analytical dashboards. Historical application, evaluation, activity, and outcome data may eventually be used to evaluate both job-search performance and the effectiveness of the application's decision logic.

### Initial Technology Direction

The current technology direction includes:

- Python
- FastAPI
- PostgreSQL
- SQLAlchemy
- REST APIs
- Pytest
- Selenium
- Power BI for future business intelligence work

Python was favored because it can support the application backend, automated testing, future data analysis, and potential machine-learning work while remaining relatively readable during review of AI-assisted implementation.

Technology selections will be formalized through Architecture Decision Records as architecture planning progresses.

### Development Approach

An incremental development strategy was selected.

The first objective will be a minimum viable product rather than implementation of the complete long-term vision. Subsequent capabilities will be introduced through planned releases while preserving a usable application.

The Linux development machine will serve as the primary build environment. The application will periodically be exercised on the Windows environment as development progresses.

The project will use an AI-assisted engineering workflow. ChatGPT will primarily support requirements, architecture, test strategy, documentation, implementation planning, and review. Claude will primarily support implementation. Product direction, architectural approval, exploratory testing, acceptance, and release decisions remain subject to human review.

AI involvement will be documented explicitly so that project documentation does not imply either greater or lesser human contribution than actually occurred.

### Documentation Approach

Project documentation will be maintained within the repository from the beginning of the project.

Documentation will use Markdown and a professional, impersonal technical writing style. Personal names and first-person language will be avoided.

The repository will include:

- Product and architecture documentation
- Architecture Decision Records
- A chronological project journal
- Lessons learned
- Development-process documentation
- Release documentation

Decisions that are later replaced should generally remain in the historical record with their superseded status rather than being removed.

### Source Control and Publication

The project was initialized locally as a Git repository before implementation began.

The GitHub repository will initially remain private. This provides an opportunity to develop and review the application without prematurely exposing unfinished work or private information.

A public release is planned after the MVP reaches an appropriate level of quality and the complete repository and Git history have undergone a privacy and security review.

The project will remain a single evolving repository rather than creating separate repositories for each application version. Stable releases will be identified through version tags.

### Privacy

Privacy is a design requirement.

Real job-search information must remain separate from publicly shareable source code and documentation. Synthetic data will eventually support development, automated testing, screenshots, demonstrations, and portfolio presentation.

Before any public release, the repository will be reviewed for personal information, credentials, private communications, real job-search data, database exports, logs, screenshots, metadata, and other information that should not be publicly exposed.

### Timezone Fix: Create-Application "Today" Comparison

- Root cause: `create_application`'s default `now` (used whenever a caller
  doesn't inject one - i.e. every real request through the Flask routes)
  was constructed as `datetime.now(timezone.utc)`, then compared via
  `now.date()` against `application_date` - a value with no timezone of its
  own, populated from the create form's `date.today()` default, which is
  local. Comparing a local-meaning date against a UTC-derived date is a
  frame mismatch, not a UTC-vs-local "which is correct" question: the
  comparison itself (`application_date == now.date()`) was already correct
  given a properly local-aware `now`; only the *default* was wrong.
- Fix: changed the default to `datetime.now().astimezone()`, the standard
  idiom for "the current moment, as an aware datetime in the system's local
  timezone." `_format_timestamp` already normalizes any aware datetime to
  UTC before storage regardless of its original tzinfo, so persisted
  timestamps are unaffected - only the "is this today" comparison changes,
  and now agrees with the value the form itself used to decide what
  "today" means.
- Scope discipline: `change_application_status`'s default `now` (added for
  FR-007) uses the same `datetime.now(timezone.utc)` pattern, but has no
  equivalent bug - it's only used for the future-timestamp rejection, and
  aware-datetime comparisons are timezone-correct regardless of which zone
  `now` is expressed in. Left unchanged rather than "fixed" for
  consistency, since nothing there is actually broken.
- Added a wall-clock test (`test_default_now_uses_local_today_not_utc_today`)
  that omits the `now` override entirely, exercising the real default
  against the real local `date.today()`, and a second test
  (`test_today_comparison_respects_nows_own_timezone_not_utc`) using an
  explicit non-UTC-offset `now` to prove the comparison logic itself
  correctly respects a properly local-aware value.

### Test-Reliability Fix: Deterministic Timezone Regression Test

Independent final review identified that neither of the two tests added
above reliably guards against the bug being reintroduced:

- `test_default_now_uses_local_today_not_utc_today` only fails under the
  old code during the roughly-four-hour daily UTC/local boundary window -
  outside that window it would pass under old *and* new code alike, giving
  false confidence. (Its description above was corrected to reflect this;
  it was previously mischaracterized as reliably catching the regression
  "regardless of time of day," which isn't accurate.)
- `test_today_comparison_respects_nows_own_timezone_not_utc` passes `now`
  explicitly, so `now or <default>` never evaluates the default expression
  at all - confirmed by direct experiment that this test passes identically
  whether the old or new default is in place. It was mischaracterized as a
  "fully deterministic" proof of the fix; it actually guards a different,
  narrower property (the comparison itself respects an arbitrary
  local-aware `now`) and provides no protection against the actual bug.

Added `test_default_now_is_constructed_as_local_not_utc`, a deterministic
test using `unittest.mock.patch("job_hub.applications.datetime",
wraps=datetime)` (stdlib, no new dependency). `wraps=datetime` keeps all
real `datetime` behavior intact while recording how `datetime.now` is
called; the test asserts `datetime.now` was called with **zero arguments**
(`assert_called_once_with()`), which only holds for the fixed
`datetime.now().astimezone()` expression - the old `datetime.now(timezone.utc)`
default calls `now` with one positional argument and would fail this
assertion regardless of wall-clock time or system timezone.

Verified directly, not just asserted: temporarily reverted the production
fix (`datetime.now(timezone.utc)`) and confirmed the new test fails
cleanly, surfacing the exact same `ValidationError` the real defect
originally produced - then restored the fix and confirmed the test (and
the full suite) pass again. This is the test that now actually protects
against regression; the other two remain useful as complementary
end-to-end and comparison-logic checks but are no longer relied on for
that purpose. No production code was changed in this pass.

Pytest result: 190 tests passed (189 + 1 new deterministic regression
test).

  category filters, a job-location filter design question) is a
  substantially larger UI surface better tackled as its own focused slice.

  section: when the new application supplies an external job/requisition

### FR-010 Completion: Reference-Data Selection in the Application Form

- The completion audit found FR-010 partially implemented: the data layer
  already normalizes and reuses company, source, and location records (a
  duplicate `company_name`/`source_name`/location triple reuses the
  existing row rather than creating a new one - this was already true of
  `create_application`/`edit_application` before this change), but nothing
  in the UI let a user discover or select an *existing* value while filling
  out the application form. The form's `company_name`/`source_name`/
  location inputs were plain free-text fields with no visibility into what
  already existed, so reuse only happened by accident (typing an identical
  string) rather than by deliberate selection - the gap FR-010 actually
  names ("the user shall be able to select an existing company, location,
  or source").
- **Mechanism decision: native HTML5 `<datalist>`, not `<select>` or an
  admin screen.** Re-read FR-010's exact wording plus architecture.md's
  reference-data section before choosing. Two requirements ruled out the
  alternatives:
  - FR-010 also requires "the user shall be able to create the required
    company, location, or source as part of the application workflow" and
    that creation "shall not require the user to leave" that workflow. A
    `<select>`-only dropdown can't accept a new free-text value without
    JavaScript, so it would satisfy selection but break in-workflow
    creation.
  - architecture.md states reference-data normalization "shall not force a
    separate administration workflow." A dedicated reference-data admin
    screen was therefore not an option regardless of how it might make
    selection easier.
  `<input list="...">` bound to a `<datalist>` satisfies both: it offers
  existing values as browser-native autocomplete suggestions while still
  accepting arbitrary typed text, and it requires zero JavaScript,
  consistent with the project's minimal-JS constraint and NFR-004's
  Chromium-only compatibility target. Submission and server-side handling
  are completely unchanged - the field posts plain text either way, so the
  existing `create_application`/`edit_application` reuse-by-normalized-match
  logic needed no modification at all.
- **Data-scope decision: suggestion lists include every existing record,
  not just ones currently linked to an application.** FR-004 already has
  analogous-looking functions (`list_source_filter_options`,
  `list_job_location_filter_options`) that intentionally scope to values
  *currently in use*, so a list filter never offers a dead-end option.
  FR-010 has the opposite requirement: a company/source/location that was
  reassigned away from every application it was once linked to (e.g. via
  an edit) is still a real, previously-created record, and offering it for
  reuse is exactly what prevents an accidental near-duplicate from being
  created. Reusing the FR-004 functions (even via an added parameter)
  would have conflated two genuinely different semantics behind one name,
  so new, dedicated functions were added instead: `list_all_company_names`,
  `list_all_source_names`, and `list_location_component_options` (the
  latter returning a new `LocationComponentOptions` dataclass with
  `cities`/`state_provinces`/`countries` lists, matching the form's
  existing three-separate-fields structure for each location fieldset).
  All three query their respective tables directly and are agnostic to
  current application linkage.
- Implementation, in the established layered pattern:
  - `src/job_hub/applications.py`: added the three functions above.
    `list_location_component_options` queries `DISTINCT city`/
    `state_province`/`country` from `location` independently (not as
    joined triples), since the three fields are suggested independently in
    the form, and explicitly filters out `NULL` per column so a location
    with only `country` set doesn't contribute a blank city/state_province
    suggestion.
  - `src/job_hub/routes.py`: `new_application` and `application_edit` both
    pass `company_name_options`, `source_name_options`, and
    `location_options` into their `render_template()` calls, unchanged
    otherwise.
  - `src/job_hub/templates/applications/_form_macros.html`: added a new
    `reference_data_datalists()` macro defining five `<datalist>` elements
    (company name, source name, and the three location components).
    Rendered once per page, since `job_location_fields()` and
    `company_headquarters_fields()` both need to reference the *same*
    three location datalists (a location can serve as either job location
    or company headquarters without distinction, per architecture.md) -
    defining them once avoids duplicate `id` attributes that would result
    from each fieldset macro defining its own copy. Added the matching
    `list="..."` attributes to the six relevant inputs (`company_name`,
    `source_name`, and both fieldsets' city/state_province/country
    inputs). `position_detail_fields()` was not touched - none of its
    fields are reference data.
  - `src/job_hub/templates/applications/new.html` and `edit.html`: both
    call `{{ forms.reference_data_datalists() }}` once, immediately before
    their `<form>` tag, and add the corresponding `list="..."` attribute
    to their own `company_name`/`source_name` inputs.
- Verified by hand via the Flask test client before writing formal tests:
  datalists render with the correct existing values; selecting an existing

  including after normalized case/whitespace variants); typing a brand-new

- Added `tests/test_reference_data_selection.py` (new file, 11 tests)
