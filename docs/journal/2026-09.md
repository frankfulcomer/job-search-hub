# Project Journal — September 2026

## 2026-09-19 — Project Initiation

### Origin

Job Search Hub originated from several related needs that converged into a single project.

The existing spreadsheet-based Job Search Hub had grown increasingly complex as additional applications, companies, recruiter contacts, activities, and supporting information were added. A relational database was identified as a more appropriate long-term system of record and as an opportunity to apply and demonstrate SQL skills.

A separate need existed for a realistic application against which Selenium automation could be developed. Rather than creating a disposable demonstration application, the decision was made to build an application that serves an actual job-search need.

Job Hunter also requires a persistent system with which future job-discovery capabilities can integrate. Job Search Hub can provide that backend and become the authoritative destination for opportunities discovered through Job Hunter or other sources.

### Expanded Direction

Discussion of the initial concept identified several longer-term opportunities.

Repeatable job-search decisions currently requiring manual or AI-assisted evaluation may eventually be moved into deterministic application logic. Potential examples include compensation thresholds, commute evaluation, duplicate detection, follow-up timing, opportunity scoring, and application workflow.

AI may remain useful for tasks involving interpretation of unstructured or ambiguous information, such as extracting structured requirements from job descriptions. The long-term objective is to use deterministic, testable logic where practical and reserve AI for tasks where it provides meaningful value.

Reporting and business intelligence were also identified as natural extensions of the relational data model. PostgreSQL can support operational SQL reporting, while Power BI is being considered for future analytical dashboards. Historical application, evaluation, activity, and outcome data may eventually be used to evaluate both job-search performance and the effectiveness of the application's decision logic.

### Initial Technology Direction

The current technology direction includes:

- Python
- FastAPI
- PostgreSQL
- SQLAlchemy
- REST APIs
- Pytest
- Selenium
- Power BI for future business intelligence work

Python was favored because it can support the application backend, automated testing, future data analysis, and potential machine-learning work while remaining relatively readable during review of AI-assisted implementation.

Technology selections will be formalized through Architecture Decision Records as architecture planning progresses.

### Development Approach

An incremental development strategy was selected.

The first objective will be a minimum viable product rather than implementation of the complete long-term vision. Subsequent capabilities will be introduced through planned releases while preserving a usable application.

The Linux development machine will serve as the primary build environment. The application will periodically be exercised on the Windows environment as development progresses.

The project will use an AI-assisted engineering workflow. ChatGPT will primarily support requirements, architecture, test strategy, documentation, implementation planning, and review. Claude will primarily support implementation. Product direction, architectural approval, exploratory testing, acceptance, and release decisions remain subject to human review.

AI involvement will be documented explicitly so that project documentation does not imply either greater or lesser human contribution than actually occurred.

### Documentation Approach

Project documentation will be maintained within the repository from the beginning of the project.

Documentation will use Markdown and a professional, impersonal technical writing style. Personal names and first-person language will be avoided.

The repository will include:

- Product and architecture documentation
- Architecture Decision Records
- A chronological project journal
- Lessons learned
- Development-process documentation
- Release documentation

Decisions that are later replaced should generally remain in the historical record with their superseded status rather than being removed.

### Source Control and Publication

The project was initialized locally as a Git repository before implementation began.

The GitHub repository will initially remain private. This provides an opportunity to develop and review the application without prematurely exposing unfinished work or private information.

A public release is planned after the MVP reaches an appropriate level of quality and the complete repository and Git history have undergone a privacy and security review.

The project will remain a single evolving repository rather than creating separate repositories for each application version. Stable releases will be identified through version tags.

### Privacy

Privacy is a design requirement.

Real job-search information must remain separate from publicly shareable source code and documentation. Synthetic data will eventually support development, automated testing, screenshots, demonstrations, and portfolio presentation.

Before any public release, the repository will be reviewed for personal information, credentials, private communications, real job-search data, database exports, logs, screenshots, metadata, and other information that should not be publicly exposed.

### Timezone Fix: Create-Application "Today" Comparison

- Root cause: `create_application`'s default `now` (used whenever a caller
  doesn't inject one - i.e. every real request through the Flask routes)
  was constructed as `datetime.now(timezone.utc)`, then compared via
  `now.date()` against `application_date` - a value with no timezone of its
  own, populated from the create form's `date.today()` default, which is
  local. Comparing a local-meaning date against a UTC-derived date is a
  frame mismatch, not a UTC-vs-local "which is correct" question: the
  comparison itself (`application_date == now.date()`) was already correct
  given a properly local-aware `now`; only the *default* was wrong.
- Fix: changed the default to `datetime.now().astimezone()`, the standard
  idiom for "the current moment, as an aware datetime in the system's local
  timezone." `_format_timestamp` already normalizes any aware datetime to
  UTC before storage regardless of its original tzinfo, so persisted
  timestamps are unaffected - only the "is this today" comparison changes,
  and now agrees with the value the form itself used to decide what
  "today" means.
- Scope discipline: `change_application_status`'s default `now` (added for
  FR-007) uses the same `datetime.now(timezone.utc)` pattern, but has no
  equivalent bug - it's only used for the future-timestamp rejection, and
  aware-datetime comparisons are timezone-correct regardless of which zone
  `now` is expressed in. Left unchanged rather than "fixed" for
  consistency, since nothing there is actually broken.
- Added a wall-clock test (`test_default_now_uses_local_today_not_utc_today`)
  that omits the `now` override entirely, exercising the real default
  against the real local `date.today()`, and a second test
  (`test_today_comparison_respects_nows_own_timezone_not_utc`) using an
  explicit non-UTC-offset `now` to prove the comparison logic itself
  correctly respects a properly local-aware value.

### Test-Reliability Fix: Deterministic Timezone Regression Test

Independent final review identified that neither of the two tests added
above reliably guards against the bug being reintroduced:

- `test_default_now_uses_local_today_not_utc_today` only fails under the
  old code during the roughly-four-hour daily UTC/local boundary window -
  outside that window it would pass under old *and* new code alike, giving
  false confidence. (Its description above was corrected to reflect this;
  it was previously mischaracterized as reliably catching the regression
  "regardless of time of day," which isn't accurate.)
- `test_today_comparison_respects_nows_own_timezone_not_utc` passes `now`
  explicitly, so `now or <default>` never evaluates the default expression
  at all - confirmed by direct experiment that this test passes identically
  whether the old or new default is in place. It was mischaracterized as a
  "fully deterministic" proof of the fix; it actually guards a different,
  narrower property (the comparison itself respects an arbitrary
  local-aware `now`) and provides no protection against the actual bug.

Added `test_default_now_is_constructed_as_local_not_utc`, a deterministic
test using `unittest.mock.patch("job_hub.applications.datetime",
wraps=datetime)` (stdlib, no new dependency). `wraps=datetime` keeps all
real `datetime` behavior intact while recording how `datetime.now` is
called; the test asserts `datetime.now` was called with **zero arguments**
(`assert_called_once_with()`), which only holds for the fixed
`datetime.now().astimezone()` expression - the old `datetime.now(timezone.utc)`
default calls `now` with one positional argument and would fail this
assertion regardless of wall-clock time or system timezone.

Verified directly, not just asserted: temporarily reverted the production
fix (`datetime.now(timezone.utc)`) and confirmed the new test fails
cleanly, surfacing the exact same `ValidationError` the real defect
originally produced - then restored the fix and confirmed the test (and
the full suite) pass again. This is the test that now actually protects
against regression; the other two remain useful as complementary
end-to-end and comparison-logic checks but are no longer relied on for
that purpose. No production code was changed in this pass.

Pytest result: 190 tests passed (189 + 1 new deterministic regression
test).

### Application Status History Correction

- Implemented FR-008 ("Correct Application Status History"): correction via
  `GET/POST /applications/<id>/status/<history_id>/edit` and deletion via
  `GET/POST /applications/<id>/status/<history_id>/delete`, reachable from
  new "Correct"/"Delete" links added to each row of the detail page's status
  history table.
- Chosen as the next slice over the next-numbered requirement because FR-007
  made status-history entry frequent and user-driven for the first time,
  creating real, everyday opportunities for mistakes worth correcting, and
  because architecture.md documents FR-007 and FR-008 together under one
  "Status Lifecycle Behavior" section rather than as unrelated features.
- Correction pre-fills the entry's existing status, effective date/time, and
  notes, unlike FR-007's blank-by-default new-status form - there is an
  existing value to show, and requiring the user to re-enter unrelated
  fields to fix one would be poor usability with no corresponding
  requirement forcing it.
- Deletion uses a simple GET-confirm-page-then-POST flow, deliberately
  simpler than FR-006's mid-transaction confirmation: FR-006 needed to
  *discover* a fact (whether the target company is shared) before it could
  even describe what confirmation was for, so the check had to happen
  inside the write transaction. A delete-by-id target is already fully
  identified by the URL, so an ordinary pre-write confirmation page is
  sufficient and there is nothing to gain from the heavier pattern.
- Correcting or deleting the application's *current* status-history entry is
  explicitly allowed rather than specially blocked - current-status
  recalculation required zero new code, since it already falls out of the
  existing `ROW_NUMBER() OVER (PARTITION BY application_id ORDER BY
  effective_at DESC)` derivation shared by the list and detail views, the
  same property FR-007 relied on for backdated entries. Verified explicitly:
  correcting the current entry's status changes `current_status_name`, and
  deleting it falls back to the next most recent remaining entry.
- Enforced "an application must always retain at least one status history
  record" at both layers, per the confirmed decision: the service layer
  raises a new `LastRemainingStatusHistoryRecordError` when a delete would
  leave zero records (checked and rolled back within the same transaction,
  so nothing is removed even transiently), and the UI independently hides
  the per-row "Delete" link, and shows a blocked message instead of a
  confirm control on the confirmation page itself, whenever an application
  has exactly one status-history entry - so the guard doesn't depend on a
  user never reaching the route directly.
- Reused FR-007's validation exactly for the correction form: required
  status/effective-date-at fields, future-`effective_at` rejection via the
  existing `_reject_future_effective_at` helper, and the database's
  `UNIQUE(application_id, effective_at)` constraint surfaced as a generic
  `sqlite3.IntegrityError` message at the route layer - no new validation
  rules were introduced.
- `application.last_updated_at` is untouched by both operations, consistent
  with FR-007's precedent for status-history writes; verified directly for
  both correction and deletion.
- Added service-level tests (`correct_status_history`, `delete_status_history`)
  and route/template tests covering: pre-filled correction values,
  correcting current vs. non-current entries and the resulting current-status
  recalculation, correcting an entry that belongs to a different application
  (returns `None`, not a cross-application update), future/missing/blank/
  unknown-status validation, the duplicate-`effective_at` database
  constraint on correction, deleting non-current and current entries, the
  last-remaining-record guard at both layers (service exception and blocked
  UI), 404s for nonexistent application or history ids, `archived_at` and
  `last_updated_at` being left untouched, navigation (detail-page action
  links, cancel links), and the per-row Delete-link visibility rule.
- Explicitly out of scope for this slice, per the confirmed instruction:
  FR-009 (archive/restore), FR-004 (search/filter), FR-002 (duplicate
  detection), and any other deferred requirement.
- Pytest result: 234 tests passed (190 + 44 new FR-008 tests).
- Independent review against requirements, architecture, and test strategy
  found the implemented behavior correct throughout (verified directly, not
  just re-read) but identified two Medium-severity regression-coverage gaps
  for explicitly-worded FR-008/architecture.md requirements, both closed
  with new tests (no production code changed):
  - FR-008's "correcting a status-history record shall preserve the
    record's original `created_at` timestamp and update its
    `last_updated_at` timestamp" was previously verified only manually.
    Added `test_correct_preserves_created_at_and_advances_last_updated_at_on_history_row`,
    following the same deterministic pattern already established for
    `edit_application` (`time.sleep(0.01)` between the before/after reads,
    asserting `>` rather than `!=`).
  - The cross-application history-id isolation guard (a `history_id` valid
    for one application rejected when addressed through a different
    application's URL) had a service-level test for `correct_status_history`
    but none for `delete_status_history`, and no route-level test for either
    operation - notable because deletion is the destructive, harder-to-undo
    path. Added the missing service-level test plus three route-level
    tests (GET correct, GET delete-confirm, POST delete) confirming 404 and,
    for the POST case, that the other application's history row is left
    intact.
  - Pytest result after the fix: 239 tests passed (234 + 5 new regression
    tests).

### Archive and Restore an Application

- Implemented FR-009 ("Archive and Restore an Application"): archiving via
  `GET/POST /applications/<id>/archive` (confirmation page, then commit) and
  restoring via `POST /applications/<id>/restore` (single action, no
  confirmation page), reachable from new "Archive Application"/"Restore
  Application" controls on the detail page.
- Chosen as the next slice over FR-004 (search/filter) and FR-002 (duplicate
  detection) based on functional dependency, not requirement number.
  Architecture.md ties FR-004's record-state filter (Active/Archived/All)
  directly to FR-009 ("Archived and All record-state filters expose
  historical applications using the same search, filter, sort, and
  pagination behavior"), and nothing in the system could previously produce
  an archived application - `list_applications` hardcoded
  `archived_at IS NULL` with no way to relax it. Building FR-004's full
  search/filter UI first would have meant either shipping a record-state
  filter with no data to ever show, or deferring just that one FR-004
  sub-requirement - an incoherent split. FR-002 remains fully self-contained
  (touches only application entry, nothing else in Phase 1 depends on it),
  making it safe to defer indefinitely without creating a half-finished
  dependent feature.
- Implemented archiving/restoring with zero new schema: `archived_at` and
  its no-op-safe `last_updated_at` trigger already existed from the SQLite
  persistence foundation slice, unused until now.
- `archive_application`/`restore_application` are true no-ops when the
  target is already in the requested state: the `UPDATE` is guarded with
  `AND archived_at IS NULL` (archive) / `AND archived_at IS NOT NULL`
  (restore), so re-archiving an already-archived application (or
  restoring an already-active one) neither changes `archived_at` to a new
  timestamp nor advances `last_updated_at` - matching the project's existing
  "reusing an unchanged record does not constitute a modification"
  timestamp philosophy. Verified directly for both operations.
- Confirmation shape follows the requirement text's own asymmetry: FR-009
  explicitly requires confirmation before archiving (GET-confirm-page-then-
  POST, the same pattern established for FR-008 deletion, since the target
  is already fully identified by the URL - nothing needs discovering, so
  FR-006's heavier mid-transaction pattern wasn't warranted); restoring has
  no equivalent confirmation sentence, so it's a single POST-only action
  with no separate confirm page. "Cancel a restore operation" is trivially
  satisfied by not clicking Restore.
- Implemented the minimal FR-009-required "archived-application view or
  filter" as a record-state toggle (`?state=active|archived|all`) on the
  existing application list, deliberately scoped to just that - no free-text
  search, no status/source/work-arrangement/employment-type/date-range
  filtering, all of which remain deferred to FR-004. The toggle reuses
  `list_applications`'s existing sort and pagination code path rather than a
  separate query/view, per architecture.md's explicit guidance, so FR-004
  can extend this mechanism later instead of replacing it. Default state is
  Active, matching FR-009/FR-004's stated default.
- Archived rows are visually distinguished when shown alongside active ones
  (`class="archived-row"` plus an "(archived)" badge next to the job title
  in the `All` state), satisfying architecture.md's "mixed lists visually
  distinguish archived records" for the minimal filter implemented here.
- The detail view already didn't filter by `archived_at` (an explicit FR-005
  design decision preserved unchanged), so an archived application's detail
  page continues to work normally and now also shows a
  `#detail-archived-notice` indicator plus the Restore control.
- Deliberately did not add any restriction on editing, changing status, or
  correcting status history for an archived application - FR-009 doesn't
  require this, and adding it would be an unrequested restriction beyond
  the stated scope.
- Added service-level tests (`archive_application`, `restore_application`)
  and route-level tests covering: archiving/restoring an application,
  `created_at` preservation and `last_updated_at` advancement (and its
  absence on no-op re-archive/re-restore), preserved application information
  and status history, 404s for nonexistent applications, the confirm-then-
  commit flow for archive (including that a plain GET never archives),
  POST-only enforcement for restore (405 on GET), detail-page control
  visibility (Archive vs. Restore, archived notice), the default/archived/
  all record-state list views, visual distinction of archived rows,
  fallback to Active for an unrecognized `state` value, the empty-state
  message when no archived applications exist, and out-of-range pagination
  combined with a record-state filter. Also extended `list_applications`'s
  existing test file with `record_state` coverage (default value, each of
  the three states, the `is_archived` flag, unrecognized-value fallback, and
  sort/pagination behaving identically under the `archived` state).
- Explicitly out of scope for this slice, per the confirmed instruction:
  FR-004's free-text search and category filters (only the minimal
  record-state visibility was implemented) and FR-002 (duplicate detection).
- Pytest result: 279 tests passed (239 + 40 new FR-009 tests).
- Independent review against requirements, architecture, and test strategy
  found the implemented behavior correct throughout but identified two
  findings, both fixed before commit:
  - Medium: the approved scope for this slice included Restore being
    reachable "both from the minimal archived list view and directly on an
    application's own detail page," but only the detail-page control had
    been built - `list.html` showed an "(archived)" badge with no per-row
    action. Fixed by adding an "Actions" column (shown only in the
    `archived`/`all` states, to avoid an always-empty column in the default
    `active` view) with an inline Restore button on each archived row,
    reusing the existing `application_restore` route.
  - Low/Medium: no regression test verified that `archived_at`'s persisted
    value actually reflects "the date and time when the application was
    archived," as FR-009 requires - existing tests only checked it was
    non-null. A regression that stored the wrong value (verified via a
    deliberately-broken `archive_application` that copies `created_at`
    instead) would have passed every prior test. Added a service-level test
    asserting the exact stored value against an injected `now`, and a
    route-level test asserting the persisted value falls within a
    before/after wall-clock window around the real HTTP request (since
    `now` isn't injectable through the route layer).
  - Pytest result after the fixes: 285 tests passed (279 + 6 new regression
    tests).
