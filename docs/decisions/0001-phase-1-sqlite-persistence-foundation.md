# 0001. Phase 1 SQLite Persistence Foundation

## Status

Accepted.

## Context

[Architecture](../architecture.md) defines the Phase 1 logical schema for six
entities (`COMPANY`, `LOCATION`, `APPLICATION`, `SOURCE`, `STATUS`,
`APPLICATION_STATUS_HISTORY`) and a set of integrity rules, but explicitly
leaves several physical-schema details to implementation:

- The concrete timestamp representation and timezone handling.
- The exact `employment_type` value set.
- How missing `LOCATION` components are treated when enforcing normalized
  equivalence.
- How compensation values are guaranteed to be genuinely numeric rather than
  merely declared as such.

This ADR records the decisions made when implementing the SQLite schema so
they are traceable rather than implicit in the DDL.

## Decision

### Timestamp convention

All timestamp columns (`created_at`, `last_updated_at`, `effective_at`,
`archived_at`) are stored as `TEXT` in ISO-8601 UTC with millisecond
precision and a literal `Z` suffix: `YYYY-MM-DDTHH:MM:SS.sssZ`, generated by
SQLite's `strftime('%Y-%m-%dT%H:%M:%fZ', 'now')` (SQLite's `now` modifier is
UTC by default). `application_date`, which is documented as a date rather
than a timestamp, is stored as `YYYY-MM-DD` `TEXT` with no time component.

`created_at` and `last_updated_at` are populated by a column `DEFAULT` on
insert and maintained by an `AFTER UPDATE` trigger on each table, so
"maintained automatically" does not depend on future application code
remembering to set them. A `CHECK (... GLOB ...)` constraint on
`application_date` and `effective_at` provides baseline structural format
validation at the database layer; full calendar/business validation
(including the future-timestamp prohibition) remains an application-level
concern, consistent with the architecture's testability guidance on
controllable time boundaries.

Each `AFTER UPDATE` trigger has a `WHEN` clause comparing every non-metadata
column between `OLD` and `NEW` (using `IS NOT` so `NULL` comparisons behave
correctly) and only advances `last_updated_at` when at least one of them
actually changed. This directly implements the architecture's statement that
"reusing an unchanged reference record does not constitute a modification to
that record": a no-op `UPDATE` (e.g., re-saving a record with identical
values) leaves `last_updated_at` untouched, while a genuine value change
advances it.

### Insignificant whitespace convention

Where the architecture requires normalized comparison or rejection of blank
required text (company name, source name, status name, job title, and
`LOCATION` components), "insignificant leading or trailing whitespace" is
defined for Phase 1 as space, tab, carriage return, and line feed
(`char(32) || char(9) || char(13) || char(10)`). SQLite's single-argument
`trim(x)` only strips plain spaces, so every blank-rejection `CHECK` and
every normalized-uniqueness index expression passes this character set
explicitly to `trim(x, y)`, keeping the two consistent — a value that
differs from an existing record only by this whitespace class is treated as
insignificant by both the blank check and the uniqueness comparison.

### `employment_type` value set

The architecture defers the exact value set to implementation. Phase 1 uses
`FULL_TIME`, `PART_TIME`, `CONTRACT`, `TEMPORARY`, matching the examples
given in the MVP field definition.

### `LOCATION` nullability and equivalence

`city`, `state_province`, and `country` are each individually nullable, since
the architecture discusses "missing components" without marking any single
field required. A `CHECK` constraint requires at least one non-blank
component, preventing a fully-empty `LOCATION` row — this enforces the
architecture's stated principle that unknown location is represented by a
null foreign key rather than a placeholder location record. This constraint
is an implementation inference, not literal architecture text.

Normalized reuse/uniqueness is enforced with a `UNIQUE` index over
`lower(trim(coalesce(component, '')))` for all three components, so that
absent components are treated consistently (rather than SQL's default
per-row-distinct `NULL` behavior) when determining equivalence.

Company and source name uniqueness use the equivalent single-column pattern:
a `UNIQUE` index on `lower(trim(name, ...))`, using the whitespace character
set defined above.

### Known limitation: non-ASCII case folding

SQLite's built-in `lower()` performs ASCII-only case folding; it does not
casefold non-ASCII letters (for example, `É`/`é`). As a result, two company,
source, or location names that differ only in the casing of non-ASCII
characters (e.g., `"CAFÉ CORP"` vs. `"Café Corp"`) are not detected as
duplicates by the normalized-uniqueness indexes, even though ordinary
ASCII-only names are correctly deduplicated regardless of case and the
whitespace conventions above. Resolving this fully would require SQLite's
ICU extension or a custom collation — both disproportionate to Phase 1
scope. This is an accepted Phase 1 limitation: non-ASCII names remain
case-sensitive for duplicate-detection purposes. A future phase may
introduce full Unicode-aware normalization if real-world data quality
warrants it.

### Numeric compensation enforcement

The architecture states that "schema implementation shall not rely on a
numeric-looking column declaration alone to satisfy compensation
validation." SQLite's default manifest typing would allow a `REAL`-declared
column to silently store `TEXT`. Phase 1 tables use SQLite `STRICT` tables
(available in SQLite 3.37+; this environment runs 3.46.1), which reject
non-numeric writes to `compensation_min`/`compensation_max` at the database
level rather than relying on declared type alone.

### `STATUS` seed data

Initial values, in `display_order`: `APPLIED`, `SCREENING`, `INTERVIEWING`,
`OFFER` (non-terminal); `ACCEPTED`, `REJECTED`, `WITHDRAWN`, `CLOSED`
(terminal). `OFFER` is treated as non-terminal because the application is
still awaiting an applicant decision. Seeding uses `INSERT OR IGNORE`
against the `UNIQUE` `name` constraint, so re-running initialization never
duplicates or resets existing rows.

### Initialization trigger point

**Revised.** Schema creation and seeding (`job_hub.db.init_db`) originally
ran only on explicit request (`flask init-db` or a direct call), specifically
to keep plain `create_app()` calls — used by application-factory tests —
from implicitly creating or touching a database file on disk. That trade-off
was recorded as provisional, to be revisited once CRUD routes existed and
needed guaranteed schema presence at request time; the Create Application
route reached that point; a fresh checkout with no prior `flask init-db` step
would 500 on first use, which fails Phase 1's usability expectations for a
personal local application.

`create_app()` now calls `db.init_db()` unconditionally, inside an app
context, immediately after `db.init_app(app)`. This is safe to run on every
application construction because `init_db` is fully idempotent
(`CREATE TABLE IF NOT EXISTS` plus `INSERT OR IGNORE` seeding): it never
drops a table, never duplicates seed rows, and never touches existing
application data, so "ordinary application startup shall not reset existing
data" still holds. The `flask init-db` CLI command remains available for
explicit/manual use (e.g., scripting), but is no longer required for the
application to function.

The test-isolation trade-off that motivated the original explicit-only
design is instead handled by giving every test that constructs a real
`Flask` app (via `create_app()`) an isolated `DATABASE` path (a `tmp_path`
file), rather than by keeping initialization manual. No test calls
`create_app()` without a config override.

## Consequences

- Physical schema decisions are traceable to this record rather than only
  inferable from `schema.sql`.
- The `LOCATION` non-placeholder `CHECK` and the `employment_type` value set
  are implementation choices that should be reconsidered if future
  requirements introduce conflicting needs (e.g., a documented additional
  employment type).
- Schema/seed initialization now runs automatically and idempotently on
  every `create_app()` call; a fresh checkout works without a manual setup
  step. Any test that builds a real app must supply an isolated `DATABASE`
  path so it never touches the user's personal database.
- Non-ASCII case folding remains an accepted limitation (see above); this
  should be revisited only if real Phase 1 usage surfaces it as an actual
  data-quality problem, not preemptively generalized.
- Because the update triggers compare every non-metadata column, adding a
  column to any of the six tables in a future change must also add it to
  that table's trigger `WHEN` clause, or a genuine change to the new column
  alone would silently fail to advance `last_updated_at`.
